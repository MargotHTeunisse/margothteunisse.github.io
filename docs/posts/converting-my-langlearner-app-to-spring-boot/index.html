Converting my Language Learning App to Spring Boot
Converting my Language Learning App to Spring Boot

This is the second part in a series where I build a language learning app using Java and Spring Boot. Please see this post for an overview of the project.

In the previous part of my LangLearner project, I constructed a console application in Java using domain-driven and test-driven design. In this part, I want to take some time to delve into the Spring framework and Spring Boot, and how it can help to make my application more robust.

Why use a framework?

As I understand it, frameworks encompass the ‘plumbing’ of an app: technical concerns such as handling HTTP requests, connecting to a database, security, or logging, which do not depend on the domain logic. Frameworks are widely employed in modern software engineering for a few reasons:

  • Frameworks save the developer the time and effort of building their own code structure.
  • Frameworks are less susceptible to bugs than custom code.
  • Because frameworks are widely adopted, they provide a common language between developers.

I won’t get into these reasons in detail; for that, I’m happy to refer to the wonderful Spring Start Here1. The better question for me at this time is: why do I want to use Spring for my project? That informs what aspects of the Spring framework I should look to.

In my case, there are two things I want to do with Spring:

  • Handing over initialization to Spring by using the Spring Core application context
  • Creating an API using Spring MVC

In this post, I will focus on the first part. The end product for this part will be a Spring Boot console application.

Adding Beans to Spring’s application context

To understand how Spring works, it helps to note that my ‘main function’ actually has two separate responsibilities. First, it instantiates the application, by creating a Deck connected to a Vocabulary. Second, it runs the application exactly once. To make this separation more explicit, I can extract the functionality for running the application to a separate class, which I’ll call ConsoleSession.

My LangLearnerConsole class now looks like this:

public class LangLearnerConsole {
    public static void main(String [] args) {
        ConsoleSession session = new ConsoleSession(Deck(Vocabulary("wordlist.txt")));
        session.run();
    }
}

In the first line of my main function I instantiate my application, and in the second line I run it. Spring can augment both steps but for now, I will focus on the initialization step.

A foundational concept in the Spring framework is Inversion of Control (IoC). Inversion of control means that, instead of instantiating and connecting objects myself, I hand fine-grained control of select objects (called Beans) over to Spring. The basic structure of my main function then looks like this:

1
2
3
4
5
6

public class LangLearnerConsole {
    public static void main(String [] args) {
        var context = new AnnotationConfigApplicationContext(LangLearnerConsole.class);
        context.getBean(ConsoleSession.class).run();
    }
}

Note that, in this new version, I’m not specifying any details about the application in the initialization step. This is by design: it prevents me from putting doman logic in the application’s main method. Instead, I tell Spring to initialize its application context.

Currently the application context is empty, so the application can’t run yet. If I request a Bean of type ConsoleSession, Spring will return an error. To make the application run, I need to make Spring aware of the required Beans.

There are multiple ways to add Beans to Spring’s application context, but an oft-preferred method is to use stereotype annotations. Stereotype annotations are added above class definitions, and tell Spring to create exactly one instance of that class. For example, I can add an instance of ConsoleSession to Spring’s application context by annotating it with @Component2.

For Spring to instantiate a console session, it will also need a Deck. Again, I tell Spring to instantiate a Deck by annotating it with @Component.

@Component
public class Deck{
    private final IVocabulary vocabulary;
    private Card drawnCard;

    Deck(IVocabulary vocabulary) {
        this.vocabulary = vocabulary;
    }

    //Omitted Deck methods
}

I don’t need to annotate Card as a component, since I’m not using any of Spring’s functionalities for these. However, I am going to need an IVocabulary object in order to instantiate my Deck. To do that, I place a stereotype annotation above the TextVocabulary class. The interface itself is never annotated, since interfaces hold no meaning to Spring.

I annotate TextVocabulary with @Repository. This stereotype inherits from @Component, and therefore tells Spring to create exactly one instance of the class. However, using @Repository is preferable here because it also provides information about the role of TextVocabulary, both to Spring and to anyone reading the code.

@Repository
public TextVocabulary implements IVocabulary {
    //Omitted fields
    public TextVocabulary(String filename) {
       //Omitted file reading
    }
    //Omitted IVocabulary implementations
}

Finally, I need to provide Spring with a filename for TextVocabulary to read out. I can’t use a stereotype annotation for this, since that would require me to directly modify the String class. Instead, I can manually create a @Bean of type String within my LangLearnerConsole class. I annotate LangLearnerConsole as a @Configuration to indicate that it can be a source of Beans. I also annotate it as @ComponentScan to make it look for stereotype annotations.

@Configuration
@ComponentScan
public class LangLearnerConsole {
    public static void main(String [] args) {
        var context = new AnnotationConfigApplicationContext(LangLearnerConsole.class);
        context.getBean(ConsoleSession.class).run();
    }

    @Bean
    public String filename() {
        return "wordlist.txt";
    }
}

Now, Spring has enough information to construct its application context: it uses the filename I provided to instantiate a TextVocabulary, which it uses to instantiate a Deck, which in turn is used to instantiate a ConsoleSession. Note that I never explicitly specified how these objects should be connected; because the structure is so simple, Spring can ‘auto-wire’ the objects. For a more complex app this process, called dependency injection (DI), is more involved.

My console application runs now, but as a downside, the name of my vocabulary file is now hard-coded in this @Bean method. For the final part of this post, I will externalize my vocabulary file name by using Spring Boot and its application.properties file.

Externalizing my vocabulary file with Spring Boot

Spring Boot is a part of the Spring ecosystem, of which the core idea is ‘convention over configuration’. Spring itself offers extensive configuration options, but for many use cases, such customization is not necessary. Spring Boot provides many preconfigured functionalities which make it easier to set up a Spring application.

I will use two features offered by Spring Boot for my console application. Most importantly, I will use Spring Boot’s application.properties file to store my vocabulary file. I will also use Spring Boot’s CommandLineRunner interface to make my LangLearnerConsole class a little more concise.

In Spring Boot, application.properties is a standard file used for configuration. When I store the name of my vocabulary file in application.properties, I can directly access it in TextVocabulary:

1

vocabulary.filename: wordlist.txt

@Repository
public TextVocabulary implements IVocabulary {
    //Omitted fields
    public TextVocabulary(@Value("${vocabulary.filename}") String filename) {
       //Omitted file reading
    }
    //Omitted IVocabulary implementations
}

To make use of application.properties and other Spring Boot features, I need to call the SpringApplication.run method, and add the @EnableAutoConfiguration annotation. Since the combination of @Configuration, @Componentscan and @EnableAutoConfiguration is used so often, Spring Boot lets me replace all of them by @SpringBootApplication.

In addition to using application.properties, I’ve also marked my ConsoleSession class as a CommandLineRunner. This is an interface provided by Spring Boot, which signals that arun method (with potential program arguments) should automatically be run when the CommandLineRunner is part of a Spring Boot application. That exactly fits the function which my ConsoleSession fulfills.

Thanks to these Spring Boot features, my LangLearnerConsole class now requires minimal information about the underlying application.

@SpringBootApplication
public class LangLearnerConsole {

    public static void main(String[] args) {
        SpringApplication.run(LangLearnerConsole.class).close();
    }

}

With this, I’ve successfully converted my console application to a Spring Boot application. The console output is the same as in the previous part, in essence, but it’s now surrounded by information provided by Spring Boot’s autoconfiguration.
