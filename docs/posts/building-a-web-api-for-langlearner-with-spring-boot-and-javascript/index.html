Building a web API for LangLearner with Spring MVC and Spring Boot

This is the third part in a series where I build a language learning app using Java and Spring Boot. Please see this post for an overview of the project.

Previously, I’ve used the Spring framework with Spring Boot to run a console application. This console application used inversion of control and dependency injection from Spring Core, but was otherwise comparable to my version without Spring. For this next part, I make more extensive use of Spring Boot and Spring MVC in order to construct HTTP endpoints. The end result for this part is a web API, which I can call using a browser or a service such as Bruno.

Revising my Maven structure

Before I construct my API, it’s good to make sure that my web and console versions are properly separated. I’ve left the project structure to IntelliJ thus far, but if I want to make this a multi-module application, I need to take a closer look at it.

First, I’ve separated my existing console application into two modules, called core and console-app. I’ve also created a module called web-services, which will contain my API. Both console-app and web-services import from the core module.

Next, I need to take a look at my Spring dependencies. I could import the dependencies I need individually, but Spring Boot also provides convenient ‘starters’, which are bundles of common Spring dependencies. For my program thus far, IntelliJ has added spring-boot-starter, as well as spring-boot-starter-parent, from which all other starters inherit. I’ll just leave these dependencies in the parent POM file.

Defining scopes for my components

Having separated the different parts of my application, I can start to build my web API. An important part of that is to consider the scope of the components, which I haven’t discussed thus far.

By default Spring beans are singleton-scoped, which means that Spring creates a single bean when I run the application, and continues to refer to that instance for the whole lifetime of the application. For my console application this was fine, but how would this work in a web application? I can hardly have all users drawing from the same deck!

For these purposes, Spring MVC offers four web-specific scopes. The one that’s relevant for my case is the session scope. A session-scoped bean is initiated whenever a HTTP session is created, and only lasts for as long as the session lasts. I don’t want my vocabulary object to be session-scoped, since it’s a Repository object which might hold a lot of data. It seems preferable to have a single IVocabulary bean, which holds card data which is shared by all users.

By contrast, my Deck component seems like a good contender for being session-scoped. If every HTTP session has its own deck, then I don’t have to worry about users drawing from a shared deck. However, my Deck is a part of my core module, and doesn’t know that it’s being used for a web application. How would I go about making Deck session-scoped, then?

The solution I found comprises two steps. First, I make Deck prototype-scoped. The prototype scope, belonging to Spring Core, entails that a new object reference is created whenever the bean is called upon.

@Component

public class Deck {

    public Deck(IVocabulary vocabulary) {

}

In my web-services module, the prototype scoping allows me to define a separate session-scoped Bean, called userDeck, within a configuration class that I’ll call WebConfig. Now, whenever a HTTP session is initiated by a user, Spring will want to instantiate userDeck. Looking for a bean of class Deck, it finds the prototype bean deck, injects it, and creates an instance of it. Based on that specific instance, it creates a session-scoped bean, called userDeck.

@Configuration
public class WebConfig {
    @Bean
    @SessionScope
    public Deck userDeck(Deck deck) {
        deck.draw();
        return deck;
    }
}

Constructing API endpoints with Spring MVC

With the proper scoping in place, the final step is to construct the API itself. For this, I use the @Controller stereotype from Spring MVC.

When I annotate a class with @Controller, this indicates that the class should listen for HTTP requests. To create a HTTP endpoint, I simply create a method and annotate it with @RequestMapping, or with a more specific annotaiton such as GetMapping.

So what endpoints does my API implement? Based on my Card and Deck objects, I need a user to be able to draw a card. This modifies the deck, so I will annotate this as a POST request. I also need the user to read the current word, which is a GET request. Finally, I need the user to be able to submit an answer, which is also a GET request. I use a request parameter to pass the answer to the API.

For the response, I have my API return JSON data (JavaScript Object Notation) because it makes it easy to check user input. Instead of converting my data to JSON manually, I can make use of another feature of Spring MVC: the @ResponseBody annotation. When I annotate an endpoint with @ResponseBody, Spring MVC knows that it should serialize the output (i.e., convert it to a format that the HTTP protocol understands). The resulting HTTP response body isn’t necessarily in JSON format: for example, if I return a primitive, the HTTP response body will be a primitive as well. Yet, using JSON is a safe bet.

Data transfer objects

In my mockup, I use the Map class to return a single piece of JSON information for each of my API calls. Instead of the generic Map offered by Java, I can also use a dedicated object to group my data. I find this approach helpful because it allows me to easily visualize what the frontend should look like, even without writing any HTML. I will tentatively say these objects are based on the common Data Transfer Object (DTO) pattern, and that I can therefore refer to them as such.

I remark that the visibleWord and answerIsCorrect properties together provide a snapshot of the Card class, so I find it natural to group them in an class called CardDTO. In addition, I construct a class called DeckDTO, which contains CardDTO as well as deckIsDepleted. Since CardDTO is included in DeckDTO, I can imagine the resulting web page to look like this:

The actual processing of this information happens on the client side: for the implementation I currently have, I redirect to a different screen with a ‘Play Again’ button when the deck is depleted. The important part for my API, though, is that I can update the part of the page corresponding to CardView without updating DeckView, but not the other way around.

RestController vs Controller

In my API, I’ve used the @Controller annotation. It’s good to note that Spring Boot also offers a @RestController annotation, which adds the @ResponseBody annotation by default. This annotation could save me a few lines of code, yet I purposefully do not use this in my current version.

The reason for that is that the @RestController annotation is intended to be used for APIs following a REST (Representational State Transfer) architecture, and a crucial element of the REST architecture is that it is supposed to be stateless:all the information associated with a particular user’s session should be provided from the client side. Since my API strongly depends on the session-scoped userDeck object, it is decidedly not RESTful.

It’s worth considering what my application would look like with a REST architecture, and I hope to discuss this when I discuss the deployment of my application. For now though, the takeaway is that all RESTful APIs return raw data, but not all APIs which return raw data are RESTful. I therefore want to refrain from using features that are specifically intended for RESTful APIs.

AI DISCLOSURE

Early on, I used Copilot to help make sense of my Spring Boot API. At this point, I had figured out how to make my API listen for HTTP requests, but did not understand what the response should be and how to process it. In particular, I was feeling stuck because I did not understand how I could process user input. In brief, I took away the following points from this interaction:
  • Copilot (using Claude Haiku) immediately recognized that I was lacking static files, and suggested to create an index.html file, along with CSS styling and JavaScript to make a dynamic frontend. I inquired why JavaScript was necessary, and it proceeded to explain the difference between client-side and server-side architectures.
  • Moreover, since I still had my console application in my project folder, it was able to use this as an example of a server-side application.
  • At the same time, the LLM also made a mistake in assuming that my API was a REST API. This is not surprising, as I called my web API a REST API in my prompt, and my API was annotated with the RestController annotation. Yet, it did reinforce my own misgiving that a RESTful API was simply a HTTP API which returned JSON data.
Overall, I'm satisfied with my use of Copilot here. At little cost, it helped me to make sense of my application early on, and pointed me towards the right tools. This interaction also showed me how the LLM can build on the information I've provided it with, both in a positive and in a negative sense. On one hand, it was able to better grasp the intention of my project because my project folder ; on the other hand, it also unquestioningly took over my assertion that I had a RESTful API.

@Controller
@RequestMapping("/api")
public class WebAPI implements ApplicationContextAware {

    private ApplicationContext applicationContext;

    @Override
    public void setApplicationContext(@NonNull ApplicationContext applicationContext)
            throws BeansException {
        this.applicationContext = applicationContext;
    }

    @GetMapping("/drawn-card")
    @ResponseBody
    public CardDTO drawnCard() {
        Deck deck = (Deck) applicationContext.getBean("userDeck");

        Card card = deck.getDrawnCard();
        return new CardDTO(card.read());
    }

    @GetMapping("/submit")
    @ResponseBody
    public CardDTO submitAnswer(@RequestParam String answer) {
        Deck deck = (Deck) applicationContext.getBean("userDeck");

        Card card = deck.getDrawnCard();
        boolean answerIsCorrect = card.check(answer);
        return new CardDTO(card.read(), answerIsCorrect);

    }

    @PostMapping("/draw-next-card")
    @ResponseBody
    public DeckDTO drawNextCard(HttpSession session) {
        Deck deck = (Deck) applicationContext.getBean("userDeck");

        boolean deckIsDepleted = !deck.draw();
        if (deckIsDepleted) {
            session.invalidate();
        }

        return new DeckDTO(deck.getDrawnCard().read(), deckIsDepleted);
    }
}

The actual API is harder to read than my mockup; it would be good to implement tests to ensure that it keeps working the way I think it does.

When I wrote unit tests for my domain logic, I used JUnit, but that’s not sufficient in this case. After all, my API takes the userDeck object from a Spring application context; how am I going to test that? For this purpose, Spring offers a test context, which is a part of the Spring Boot test starter.

Since I’ve already tested my Deck object, I’m using Mockito to mock the userDeck object. Spring Boot offers the @MockitoBean annotation to mock a Deck object and add it as a bean in my test context. I’m also using MockHttpSession to check if the HTTP session is invalidated when the deck is depleted.

It’s good to note that my userDeck mock is a singleton, unlike the real userDeck from WebConfig which is session-scoped. This works well for testing WebAPI in isolation: I can load the application context once, and set my userDeck outputs as I please. That said, I might want to add a more involved test at a later point to make sure that my session-scoped deck is functioning the way I expect it to.
