A Console App for Language Learning with Domain-Driven and Test-Driven Design

This is the first part in a series where I build a language learning app using Java and Spring Boot. Please see this post for an overview of the project.

In this first part of my LangLearner project, I will work out the design of my application. As already mentioned in the overview, I will be using test-driven design for this. In addition, I will use UML diagrams, specifically class and sequence diagrams, to visualize my design. The end product for this part is a console application in Java.

Building the domain model

The first step in building my language learning application is to ask what my domain logic is. In other words: how will my app help someone to learn vocabulary? A good way to figure this out is to pay close attention to the nouns and verbs that people are naturally inclined to use 1.

Traditionally, if I want to learn a language I might use a deck of flash cards. Whenever I draw a card, I read the front of the card, and try to translate the word. I then check whether my translation matches the back of the card, before moving on to the next card.

So I will need a Deck, which allows me to draw a Card from it. A Card has a front and a back. I need to be able to read the front, and check that my answer matches the back. I might want to add more functionalities, like shuffling the deck, or showing the correct answer to the user, but I think this is a good minimal model to start with.

There’s still one glaring issue that I’m left with here, though: where is the Deck coming from? The way it looks now, it seems as though I need to manually provide the cards property to the Deck. That might work for a few words, but it’s clearly not very convenient for a language learning app! I’ll get back to that, but before that, I will first implement these functions.

Implementing scenarios with test-driven design

As noted in my overview, I am applying test-driven design, which means I’m writing the tests for my classes and methods before I write their implementations. To know what tests I should write, I can consider the different scenarios which may occur:

  • The user draws a card and translates it correctly.
  • The user draws a card and translates it incorrectly.
  • There are no more cards remaining in the deck.

I can work out these three scenarios more fully using sequence diagrams. I’ll start with the scenario where there are no more cards remaining in the deck, since that is the simplest case. All I need to do is tell the user that they’re done.

Now for the scenario where the user successfully draws a card. I don’t think I need to distinguish between the cases where the user translates correctly or incorrectly, as the only difference between the two right now is in the feedback that the user receives. I end up with this sequence diagram:

The Repository pattern

I mentioned that it was not quite clear where the Deck was coming from. Now it’s time to address this point. For my original LangLearner program, I would simply have the program read out my vocabulary from two columns in a .txt file. I could do the same in my current model, by providing my Deck with a .txt file to read out.

However, I would prefer not to put the logic for reading out a file in the constructor of Deck. This would hide too much complexity in my Deck object, and muddle my design. It’s better to give the responsibility for reading out and storing vocabulary to a separate domain object, which I’ll call TextVocabulary.

This is already a lot better than what I had before. Now that TextVocabulary is responsible for reading out and storing vocabulary, I can keep Deck simple.

At the same time, I now have the issue that my Deck depends on TextVocabulary. This is a problem because TextVocabulary is not a part of my domain logic. As the app develops, I might want to store my vocabulary data in a different format like SQL or NoSQL (e.g., MongoDB). I don’t want to overhaul my entire design when I reach that point.

That’s where we get to the widely-used Repository pattern. The idea of the Repository pattern is that, no matter what is happening under the hood, it behaves as though all data were directly stored in memory 12. To achieve this, I can create an interface, which I call IVocabulary.

Thanks to this IVocabulary interface, it’s now clear where the boundary of my domain model lies: IVocabulary is a part of the domain, but its implementations, including TextVocabulary, are not.

Now, I want to emphasize that using a text file for the vocabulary is not necessarily a problem, especially for language learning! When I come across a new word while reading or listening, I don’t want to have to stop what I’m doing to put these words in a database. I just want to jot the word down and move on. That’s why, to this day, I still use those same text files to keep track of my vocabulary.

So it doesn’t have to be a bad thing that my ‘database’ just reads out a text file. It only becomes an issue when I’m tied down to it.

Building a console application

The first version of my app is almost complete now. I can create a Deck from a Vocabulary, draw Cards from the deck, read the words on the front of the cards, and check whether a given translation is correct. All that I need to do now is to put it all together. I could create a class with a main function which loops over the cards:

public class LangLearnerConsole {
    public static void main(String @NonNull [] args) {
        try  {
            Deck deck = new Deck(new TextVocabulary(args[0]));

            Scanner scn = new Scanner(System.in);
            while (deck.draw()) {
                System.out.println("Translate: " + deck.readCard());
                String answer = scn.nextLine();
                if (deck.translateCard(answer)) {
                    System.out.println("Correct!");
                }
                else {
                    System.out.println("That is incorrect.");
                }
            }
            System.out.println("You have translated all words!");
        } catch (IOException e) {
            System.out.println("Could not find file.");
        }
    }
}

This produces a working Java application, though a very simple one. As an example, I have an input called wordlist.txt, which contains two comma-separated columns of words, in English and Finnish respectively.
